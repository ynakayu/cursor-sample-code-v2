# コード品質・改善調査レポート

対象: 勉強時間トラッカー（`index.html` / `app.js` / `styles.css`）  
調査日: 2026-05-23  
※ `todo-app/` は別プロジェクトのため本調査の対象外とした。

---

## 概要

メインアプリは約525行の単一 `app.js` に、UI描画・イベント処理・日付/時間フォーマット・localStorage 永続化・タイマー計測ロジックがすべて集約されている。初学者向け方針（シンプルな書き方・関数コメント）とのギャップが大きく、**可読性**と**プロジェクトルール遵守**が最優先の改善領域である。

パフォーマンス面は現状のデータ規模では致命的ではないが、`renderAll()` による全体再描画とセッション配列の繰り返し走査に、将来の記録増加時のボトルネック候補がある。

## 可読性の問題

- **`app.js` 全体（38〜522行）— 関数にコメントがない**
  - **理由**: ユーザールール「関数には必ずコメントを入れる」および初学者向け `AGENTS.md` に反する。40以上の関数がすべて無コメントで、処理の意図を追いにくい。
  - **改善案**: 各関数の直前に、何をするか・入力/出力があれば何か、を1〜2文の日本語コメントで記載する（既存の `todo-app/todo-list.js` など他サンプルと揃える）。

- **`app.js` 303〜305行 vs 307行以降 — 初期化がユーティリティ定義より前に実行される**
  - **理由**: `initManualDateDefault()` / `restoreActiveTimerFields()` / `renderAll()` の呼び出しがファイル中盤にあり、その直後（307行〜）に `pad2` や `loadState` などの補助関数が続く。関数宣言はホイストされるため動作はするが、**上から読んだときに「使っている関数の定義がまだ見えない」**構成になり、初学者の読み順と合わない。
  - **改善案**: ① ファイル末尾に `init()` をまとめる、② または「定数 → ユーティリティ → 状態操作 → UI → イベント登録 → 起動」の順にブロック分けし、区切りコメント（`// --- 日付まわり ---` など）を入れる。

- **`app.js` 460行 — `{ createId };` が意味不明**
  - **理由**: 単独のブロック式で副作用も代入もなく、読者にとってノイズ。意図が伝わらない「謎の1行」になっている。
  - **改善案**: 削除する。未使用警告対策であれば、該当箇所を整理するか ESLint 設定で対応する。

- **`app.js` 47〜49行、371〜375行など — `??`・スプレッド・デフォルト引数の多用**
  - **理由**: `AGENTS.md` は「省略記法を多用しない」とある。`fields.subject ?? ''` や `{ ...state, activeTimer }` は簡潔だが、初学者には展開の方が読みやすい場合がある。
  - **改善案**: 重要な箇所（状態更新・正規化）だけ `if` と明示的コピーに置き換える、またはコメントで「スプレッドは新しいオブジェクトを作る」と補足する。

- **`app.js` 109〜147行 — `renderDayDetail` 内で DOM 生成と `innerHTML` が混在**
  - **理由**: `createElement` で `li` を作りつつ、`top.innerHTML` / `meta.innerHTML`（132, 141行）で部分組み立て。`escapeHtml` で XSS は防いでいるが、**同じ関数内で2つの DOM 構築スタイル**が混ざり追いにくい。
  - **改善案**: `textContent` と `appendChild` に統一するか、テンプレート用の小さな `createSessionListItem(session)` 関数に切り出す。

- **`index.html` 63行 — インライン `style`**
  - **理由**: スタイルが HTML に直書きされ、`styles.css` との一貫性が崩れる。ボタン幅・余白の調整時に2箇所を見る必要がある。
  - **改善案**: `.manual-form__submit` などのクラスを `styles.css` に追加し、`style` 属性を削除する。

- **`index.html` 36行 — `id="studyFields"` が JS から未使用**
  - **理由**: ルール「操作対象には役割が分かる id」に対し、id が付いているが `app.js` の `els` に含まれていない。意図が不明瞭。
  - **改善案**: 将来ラベル操作に使うならコメントを付ける。不要なら id を外すか `class` のみにする。

## 保守性の問題

- **`app.js` 単一ファイル（1〜525行）— 責務の混在**
  - **理由**: UI（15〜305行）、フォーマット（307〜351行）、永続化・正規化（353〜458行）、タイマー純粋ロジック（462〜522行）が1ファイル。機能追加（セッション削除・編集・エクスポート）のたびに衝突しやすい。
  - **改善案**: 初学者向けを保ちつつ、**論理ブロック単位**でファイル分割（例: `timer.js` / `storage.js` / `calendar-ui.js`）するか、最低限セクションコメントで境界を明示する。HTML からは `<script>` を順序付きで複数読み込み（ルール「HTML/JS 分離」は維持）。

- **`app.js` 9行・202〜238行 — モジュール外の可変 `state`**
  - **理由**: `let state` がグローバルにあり、ハンドラから `state = setActiveTimer(...)` と再代入。純粋関数風の `addSession(state, ...)` と混在し、**どこで state が変わるか**を追うのが難しい。
  - **改善案**: `updateState(updater)` のような1箇所に集約する、または `persist` + `render` をセットにした `commit(nextState)` 関数を設ける。

- **`app.js` 196〜200行 — `renderAll()` が常に3系統を再描画**
  - **理由**: 一時停止（210〜214行）でもカレンダー・日別リストまで更新。変更箇所と描画範囲が一致しておらず、修正時に「どの render を呼ぶべきか」が分かりにくい。
  - **改善案**: `renderTimerOnly()` / `renderCalendarAndDetail()` に分割し、各ハンドラから必要なものだけ呼ぶ。

- **`app.js` 508〜521行 — 停止時の `startedAt` が一時停止後に不正確になりうる**
  - **理由**: `pauseTimer`（489〜496行）で `startedAt: null` にし、`buildSessionFromTimer`（518行）では `startedAt: activeTimer.startedAt || endedAt` としている。再開後に停止すると、**セッションの開始時刻が「再開時刻」に寄る**（元の開始時刻は `accumulatedMs` にしか残らない）。
  - **改善案**: タイマー開始時の `originalStartedAt` を別フィールドで保持する、または表示用メタデータとして `endedAt` と `durationMs` のみを信頼する設計にドキュメント化する。

- **セッションの削除・編集 API がない（`sessions` 配列は追記のみ）**
  - **理由**: 誤記録・手動入力ミスを直す手段がなく、localStorage を手動編集するしかない。機能不足は保守性・UX に直結する。
  - **改善案**: 日別リストに削除ボタン、`removeSession(state, id)` を追加（id は `normalizeSession` で既に付与: 371行）。

- **ルート `README.md` — 勉強時間トラッカーと無関係な内容**
  - **理由**: README がパスワードジェネレーター向けのまま。リポジトリ直下のメインアプリの説明・起動方法が欠け、新規参加者が迷う。
  - **改善案**: 勉強時間トラッカー用の README に差し替えるか、ルート README から各アプリへの索引を載せる。

- **テスト・型の欠如**
  - **理由**: `normalizeSession` / `getElapsedMs` / `pauseTimer` などはロジックが複雑だが、自動テストがない。リファクタ時の回帰検知が弱い。
  - **改善案**: ブラウザ不要の小さなテスト（Node で関数を export するか、別 `app-logic.test.js`）を検討。初学者向けなら「手動チェックリスト」を README に記載するだけでも可。

## パフォーマンスの懸念

- **`app.js` 196〜200行・各ハンドラ — `renderAll()` による過剰再描画**
  - **理由**: タイマー表示の更新以外でも、毎回 `renderCalendar()`（42セルの DOM 再生成: 157〜193行）と `renderDayDetail()` を実行。記録件数・操作頻度が増えると無駄が増える。
  - **改善案**: タイマー操作は `refreshTimerUI()` のみ。日付選択・セッション追加時だけカレンダー/詳細を更新。

- **`app.js` 155〜159行・448〜453行 — カレンダー描画のたびに全セッション走査**
  - **理由**: `getDatesWithSessions(state)` が毎回 `sessions` 全件を `Set` 化。セッション数千件規模ではカレンダー操作のたびに O(n)。
  - **改善案**: セッション追加/削除時に `datesWithStudy` キャッシュを更新する、または月単位でフィルタしてから Set を作る。

- **`app.js` 109〜111行・456〜458行 — 同一日付で `getSessionsForDate` が二重実行**
  - **理由**: `renderDayDetail` で一覧取得（110行）後、`getTotalMsForDate`（111行）が内部で再度 `getSessionsForDate` を呼ぶ（456〜457行）。
  - **改善案**: 1回取得した配列から合計を `reduce` する、または `getDaySummary(state, dateKey)` で一覧と合計をまとめて返す。

- **`app.js` 85〜89行 — 1秒間隔の `setInterval`**
  - **理由**: 計測中は毎秒 DOM の `textContent` 更新。現状は1要素のみで問題は小さい。タブ非表示時も動き続ける（`visibilitychange` は表示更新のみ: 289〜293行）。
  - **改善案**: `document.hidden` のときは interval を止め、表示時に `getElapsedMs` で一括補正（バッテリー・バックグラウンドタブ向け）。

- **`app.js` 420〜426行 — `localStorage` への同期書き込み**
  - **理由**: 操作のたびに全 `sessions` を JSON 化して保存。件数が非常に多いと `JSON.stringify` / `setItem` が重くなる可能性がある。
  - **改善案**: 現規模では許容。将来は debounce（例: 300ms）や差分保存を検討。`storage` イベントで複数タブ同期するなら設計を文書化。

- **`app.js` 155〜193行 — カレンダー42セルを毎回 `createElement` + `addEventListener`**
  - **理由**: `innerHTML = ''` で旧ノードは破棄されるためリークは起きにくいが、月移動・日選択のたびに42個のリスナーとノードを再作成。`DocumentFragment` 未使用。
  - **改善案**: 月・選択状態だけクラスを更新する「差分更新」にすると DOM 操作を削減できる（実装コストは中程度）。

## 補足（良い点）

- HTML と JS の分離、意味のある `id`（`timerDisplay`, `calendarGrid` など）はルールに沿っている。
- `escapeHtml`（149〜153行）により、ユーザー入力を `innerHTML` に載せる箇所でも XSS 対策がある。
- タイマー計測の `accumulatedMs` + `pausedAt` パターンは、表示用の経過時間計算としては一貫している（462〜471行）。
- `normalizeSession` / `loadState` の try-catch とバリデーション（364〜417行）は、壊れた localStorage からの復旧に有効。
